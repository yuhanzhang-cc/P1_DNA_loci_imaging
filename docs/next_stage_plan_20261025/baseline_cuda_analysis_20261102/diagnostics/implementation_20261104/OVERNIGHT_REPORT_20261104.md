## 需要明早处理的真实不确定性

1. **初始化的跨后端差异尚未解释。** 本机 H0/S0/P0 三者逐位一致，但本机 CPU 初始化的哈希与历史 CUDA 记录均不相同。核对原云端包与当前网络源码一致，差异不能据此归因于架构；也不能声称已复现历史 CUDA 初始化。实际 CUDA smoke 将检查 seed42 的历史哈希，正式训练还逐种子检查初始化与 sampler；不一致即在正式更新前停止。不得为赶进度删掉该检查或补跑普通 baseline 掩盖差异。
2. **P0 参数与机制决定仍待人工。** 正式配置未选择半径/归属/归一化；工程 fixture 的成功不等于选定半径 2。P0 启动要求真实完整的 60 例匿名评分、其文件哈希及配置绑定的人工决定，空表/合成答案不能通过。
3. **CUDA、完整 100 epoch 与进程恢复仍待服务器实测。** 本地通过 CPU 单步重放、包内入口和状态检查；没有在本机声称验证 CUDA 数值确定性、显存或完整训练耗时。后台启动、100 轮收尾和结果打包已有代码，但本轮未伪造完整正式结果来宣称这些路径完成实测。
4. **没有新的独立数据。** 评估代码支持受审查的新图像 manifest、文件哈希、历史 ID 与开发集内容排除；无法仅靠自动哈希证明生物学独立性，既往内部 test 的换名副本等仍需来源审核。保留原协议已记录的开发数据限制，不通过换 split 消除记录。

## 明早最短推进路线

1. 先看本报告、S0 diff 和初始化检查日志，确认是否接受 S0 作为范围对照；这一步不需要先决定 P0 半径。
2. 完成人工盲审，记录真实审查者、日期和不确定项，再确定 P0 配置；不要将“确有亮点”直接等同于一对一检测 TP。
3. 在匹配历史环境的 CUDA 服务器上执行包内 verify 和 S0 smoke。若初始化检查失败，带回日志和环境信息，先调查，不开始正式训练。
4. 通过后先运行 S0 seed42；按 [HANDOFF.md](HANDOFF.md) 验收技术问题和开发集输出，再决定是否展开剩余种子。
5. P0 配置确认后构建新修订包、执行其 CUDA smoke，再进行 P0 seed42 与 S0 的机制对照；通过预注册继续条件后展开剩余四次。S0/P0 合计最多六次新的三种子实验，CAP_P0 是 S0 的别名，不多算三次。

性能与科学结论仍待上述训练和审查。现阶段交付的是可检查的机制实现、评估代码与运行包，不是新的最优模型。
